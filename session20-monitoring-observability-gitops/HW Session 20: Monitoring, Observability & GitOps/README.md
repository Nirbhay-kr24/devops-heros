# Monitoring, Observability & GitOps

This repository contains the documentation, configurations, and demonstration work completed for **Monitoring, Observability, and GitOps**. It covers the fundamentals of system monitoring, the three pillars of observability, and the use of GitOps practices for managing Kubernetes environments.

---

## Task 1: Monitoring Fundamentals

`Monitoring` involves continuously collecting and analyzing system information to understand the health, performance, and availability of applications and infrastructure.

- **Metrics:** Numerical measurements collected over time to understand system performance, such as CPU usage, memory consumption, request rate, and error rate.

- **Logs:** Records of events generated by applications, containers, and infrastructure components. Logs provide useful information for identifying errors and understanding what happened in a system.

- **Alerts:** Notifications generated when a metric or system condition crosses a predefined threshold. Alerts help administrators identify and respond to potential problems quickly.

- **CPU & Memory Utilization:** CPU utilization represents the amount of processing capacity being used, while memory utilization shows how much RAM is being consumed. Monitoring both helps identify resource shortages and performance issues.

- **Application Health:** Indicates whether an application is running correctly and is ready to receive requests. Kubernetes applications commonly use health checks such as `/health` and readiness probes to verify application status.

## Task 2: Observability

`Observability` refers to the ability to understand the internal behavior and state of a system by analyzing the information it produces.

Monitoring primarily helps identify **what is happening**, while observability provides deeper information about **why it is happening**.

### The Three Pillars

1. **Metrics:** Numerical data that provides an overall view of system performance, resource usage, and trends.

2. **Logs:** Detailed records of application and system events that help investigate errors, warnings, and other activities.

3. **Traces:** Records that follow a request as it moves through different components or services. Traces are especially useful for troubleshooting distributed and microservice-based applications.

### Why Observability is Required

Modern applications often consist of multiple services, containers, databases, and infrastructure components. A problem in one component can affect several other components.

Observability combines metrics, logs, and traces to provide a complete view of system behavior. This helps teams detect problems, identify their root causes, troubleshoot failures, and reduce the time required to restore services.

### Common Tools & Kubernetes Observability

- **Metrics:** Prometheus, Grafana, Datadog
- **Logs:** Elasticsearch, Logstash, Kibana (ELK), Fluentd, Grafana Loki
- **Traces:** Jaeger, Zipkin, OpenTelemetry

### Kubernetes Observability

Kubernetes environments are dynamic because Pods and containers can be created, removed, restarted, or moved between nodes.

Kubernetes observability therefore requires monitoring both the cluster and the workloads running inside it. Tools such as **Prometheus, kube-state-metrics, cAdvisor, Grafana, and Loki** can be used to collect and visualize information about Kubernetes resources, containers, applications, and system performance.

## Task 3: GitOps Workflow

`GitOps` is a development and operations approach where Git is used to manage and maintain the desired state of infrastructure and applications.

Instead of making frequent manual changes directly to a Kubernetes cluster, configuration changes are committed to Git and automatically applied to the cluster through a GitOps controller.

- **Git as the Source of Truth:** The desired configuration of the application and infrastructure is maintained in a Git repository. This provides version history, change tracking, and an easy way to restore previous configurations.

- **Declarative Configuration:** Infrastructure and applications are described using declarative configuration files such as Kubernetes YAML manifests. These files specify the desired state instead of defining every individual command required to create it.

- **Continuous Reconciliation:** GitOps tools such as Argo CD continuously compare the desired state stored in Git with the actual state of the Kubernetes cluster. When a difference is detected, the controller works to bring the cluster back to the desired state.

- **Kubernetes + GitOps:** Kubernetes works well with GitOps because its resources are already managed using declarative configurations. Instead of manually running `kubectl apply` whenever a change is required, developers can update the configuration in Git and allow the GitOps controller to synchronize the changes with the cluster.

### GitOps Workflow

```text
Developer
    ↓
Modify Kubernetes Configuration
    ↓
Commit Changes to Git
    ↓
Git Repository
    ↓
Argo CD Detects Changes
    ↓
Synchronizes Kubernetes Cluster
    ↓
Application Runs in Desired State
```
